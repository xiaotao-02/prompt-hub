# 支付分层适配计划

## 目标边界

- 插件端继续只使用平台 Token、余额与充值入口，不在 Chrome 扩展内收集支付信息。
- 官网负责登录、套餐选择、创建订单、展示二维码和订单状态。
- `services/api` 负责订单、余额、扣点、webhook、支付通道适配。
- 第一阶段只支持 `wechat`、`alipay`、`mock`，暂不引入完整 Hyperswitch/Lago 服务。

## 分层方案

### 1. 业务层：参考 One API

围绕现有 `services/api/src/routes/proxy.ts`、`services/api/src/db.ts`、`services/api/src/billing.ts` 收敛：

- 保持“平台 Token → 模型代理 → 按 usage 扣点”的主链路。
- 明确 `usage_logs` 作为模型消费记录，记录 `model`、`upstream_id`、tokens、points。
- 后续可增加渠道倍率、模型倍率、用户分组，但本阶段先不扩展复杂运营规则。

### 2. 商业计费层：参考 Lago

在现有 `orders`、`usage_logs` 之上补齐账务语义：

- 将充值、扣费、退款、人工调整统一抽象为余额流水，例如新增 `balance_ledger`。
- `orders` 保留支付订单状态，`balance_ledger` 记录余额变动来源。
- 对账时以订单、支付回调、余额流水、用量日志四类数据互相校验。
- 当前 `fulfillOrder()` 已有幂等入账，应保留并改为写入流水后再加点。

### 3. 支付通道层：参考 Hyperswitch

把 `wechat` / `alipay` 从路由里抽成统一 provider 接口：

- `createPaymentOrder()`：创建扫码支付订单，返回二维码 URL。
- `parseWebhook()`：验签并解析支付平台回调。
- `mapPaidStatus()`：统一判断是否已支付。
- `channel` 仍只开放 `wechat`、`alipay`、`mock`。
- 后续拿到商户号和 API 后，只需要补环境变量，不改业务流程。

## 建议改动文件

- `[services/api/src/routes/payment.ts](services/api/src/routes/payment.ts)`：瘦身为订单 API 与 webhook 编排，不直接处理每个渠道细节。
- `[services/api/src/payment/wechat.ts](services/api/src/payment/wechat.ts)`：保留微信 Native 下单、验签、解密逻辑，适配统一 provider 接口。
- `[services/api/src/payment/alipay.ts](services/api/src/payment/alipay.ts)`：保留支付宝预下单、验签逻辑，适配统一 provider 接口。
- `[services/api/src/db.ts](services/api/src/db.ts)`：新增余额流水表与写入函数，强化订单入账幂等。
- `[services/api/src/config.ts](services/api/src/config.ts)`：保持微信/支付宝 env 配置，补充必要的开关与生产校验说明。
- `[website/src/scripts/recharge.ts](website/src/scripts/recharge.ts)`、`[website/src/scripts/apiAccountPanel.ts](website/src/scripts/apiAccountPanel.ts)`：保持现有充值交互，确认二维码、mock、订单轮询能适配统一响应。
- `[docs/PLATFORM_OPERATIONS.zh.md](docs/PLATFORM_OPERATIONS.zh.md)`：补充三层架构、商户参数接入 checklist、上线前验收项。

## 实施步骤

1. 梳理现有支付链路：确认 `POST /v1/orders`、`GET /v1/orders/:id`、mock 入账、微信/支付宝 webhook 的现有行为不变。
2. 新增支付 provider 抽象：把微信、支付宝、mock 收敛到统一接口，路由层只按 `channel` 选择 provider。
3. 新增余额流水：充值入账、模型扣点、未来退款都写流水，余额更新和流水写入放在同一事务内。
4. 强化 webhook 入账：记录支付平台交易号、回调时间、处理结果，保证重复回调不会重复加点。
5. 保持前端兼容：官网充值区继续使用现有接口响应，不大改 UI。
6. 更新运维文档：说明商户号、私钥、证书、回调 URL、沙箱/生产开关、上线前对账检查。
7. 验证：跑 `services/api` 支付路由测试，并补充余额流水和重复 webhook 的测试；最后执行 `npm run test`。

## 暂不做

- 不接入完整 Lago、Hyperswitch 服务。
- 不做订阅制、发票、税务、优惠券。
- 不支持 Stripe、PayPal、银行卡等海外支付通道。
- 不在扩展内放支付表单或收集卡号。
